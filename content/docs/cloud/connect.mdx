VantagePeers Cloud is the hosted, multi-tenant product. One backend, shared by every MCP client: **Claude**, **ChatGPT**, **Grok**, Codex, Claude Code and any IDE that speaks MCP. The server URL is the same everywhere:

```
https://mcp.vantagepeers.com/mcp
```

## The model: one agent per assistant and per account

Each assistant you connect acts as **its own agent**, with a name you choose. The same email can sign in on every assistant. A second account on the same assistant (for example a second ChatGPT account) is a **separate connection with its own agent**. Measured on 2026-10-31: one person connected four assistants, and each consent stamped its chosen agent on the token (Claude, two ChatGPT accounts, Grok).

## The consent page (all assistants)

Whatever the assistant, the flow ends on the same consent page:

1. Choose the **organisation**.
2. Choose the **agent** this assistant acts as. **Connect as myself** is the default.
   - A member sees only the agents already bound to them.
   - An organisation admin also sees unbound agents and can create one.
3. Approve.

## Claude (use the plugin, not a bare connector)

1. Open **Customize > Plugins > Add a marketplace** and enter `https://github.com/vantageos-agency/vantage-peers-claude`. Install **Vantage peers**.
   {/* not measured: EN labels. Measured FR labels: "Personnalisation > Plugins > Ajouter une marketplace". */}
   (French UI: *Personnalisation > Plugins > Ajouter une marketplace*.)
2. Open **Customize > Plugins > Vantage peers**, tab **Connectors**, and click **Connect**. Create your account or sign in, then complete the [consent page](#the-consent-page-all-assistants).
   (French UI: *Personnalisation > Plugins > Vantage peers > onglet Connecteurs > Se connecter*.)
3. In a chat, click **+ > Connectors** and make sure **vantage-peers** is enabled.
   (French UI: *+ > Connecteurs*.)
4. To reconnect: **Disconnect**, then **Connect** again (French UI: *Déconnecter*, *Se connecter*).

<Callout type="warning">
Installing the plugin does **not** connect it. If you skip step 2, Claude answers that the connector is not active in this conversation.
</Callout>

## ChatGPT

1. Open **Plugins**, click **+**, choose **Add custom MCP server**.
2. Name: `VantagePeers`. URL: `https://mcp.vantagepeers.com/mcp`. Authentication: **OAuth**.
3. Tick the warning checkbox, then click **Create as plugin**.
4. Sign in and complete the [consent page](#the-consent-page-all-assistants).

### Can ChatGPT write?

OpenAI's help article 12584461 states that custom MCP connectors have full (read and write) access on Business, Enterprise and Edu plans, and are read-only on Pro. We quote that as OpenAI's statement. We also observed, on 2026-10-31, a ChatGPT **Free** plan successfully writing a memory to VantagePeers Cloud (53 seconds after its token was issued). Plan rules are OpenAI's and can change: if a write is refused, check your plan first.

## Test it

Paste this into the assistant right after connecting:

```
Call whoami and tell me the agent name and the organisation you act as.
From now on, record decisions automatically in VantagePeers. Before answering
what was decided or what remains to do, search VantagePeers first.
```

The answer must name the agent you chose on the consent page and your organisation. Then ask: *"What did we decide so far?"*

## Troubleshooting

- **The invitation email link opens `https://mcp.vantagepeers.com/mcp` and shows `{"error":"Missing Authorization header..."}`** — that URL is the server, not a sign-in page. Sign in through the assistant's connector instead. A fix for the link is pending.
- **Claude: plugin installed but "the connector is not active in this conversation"** — the plugin is not connected yet. Do step 2 of the Claude section.
- **A tool you expect is missing or behaves like an old version** — a client connected before a server update caches tool definitions at connect time. Disconnect and reconnect once.
- **Writes are refused with "agents autorisés par la connexion : ..."** — the agent is missing from your organisation's roster. Nothing to do on the client side: contact the VantagePeers operator.
- **"aucun agent ne t'est attribué"** — no agent was chosen or bound. Reconnect and pick the agent on the [consent page](#the-consent-page-all-assistants).
- **`401 Unauthorized`** — access token expired or invalid. Clients refresh automatically; otherwise disconnect and reconnect.
- **`403 Forbidden`** — your scope does not cover that resource (your organisation only).

## Claude Code (CLI, developers)

**Audience:** developers with Claude Code installed locally.

The recommended way to connect Claude Code is through the Claude Code plugin marketplace. One command gives you the MCP backend connection **plus** 37+ skills, 7 quality hooks, and 9 slash commands — no manual `.mcp.json` editing required.

The plugin (`@elpiarthera/vantage-peers-plugin`) ships with a `.claude-plugin/plugin.json` manifest at root, alongside `skills/`, `agents/`, `commands/`, and `hooks/` directories. It wires the VantagePeers MCP server in automatically and registers the full suite of memory, messaging, and task tools in your Claude Code workspace.

### Install

```bash
claude plugin install @elpiarthera/vantage-peers-plugin
```

For marketplace documentation and discovery, see the [Claude Code plugin marketplaces](https://code.claude.com/docs/fr/plugin-marketplaces) reference.

### Configure Cloud credentials

After install, set your credentials in `.mcp.json` at the workspace root:

```json
{
  "mcpServers": {
    "vantage-peers": {
      "type": "http",
      "url": "https://vantage-peers-production.up.railway.app/mcp",
      "oauth": {
        "client_id": "YOUR_CLIENT_ID",
        "client_secret": "YOUR_CLIENT_SECRET"
      }
    }
  }
}
```

Restart Claude Code (`exit` then re-launch in your workspace). On first call, Claude Code runs the PKCE flow against `/authorize` and `/token`, caches the access token, and refreshes it automatically.

### Verify

```
/vantage-peers-init
```

The command runs 3 checks (MCP registration, `/health` connectivity, Bearer auth via `recall`). All 3 must return `PASS`. Then chain:

```
/daily-start
/check-messages
/check-tasks
```

### Manual fallback (no plugin)

If your Claude Code build does not support plugins, or you are working in a constrained environment, configure the MCP server manually — add `vantage-peers` to your project `.mcp.json` (or global `~/.claude.json`):

```json
{
  "mcpServers": {
    "vantage-peers": {
      "type": "http",
      "url": "https://vantage-peers-production.up.railway.app/mcp",
      "oauth": {
        "client_id": "YOUR_CLIENT_ID",
        "client_secret": "YOUR_CLIENT_SECRET"
      }
    }
  }
}
```

If your Claude Code build does not yet support the `oauth` field, pre-issue an access token via PKCE (see [Issue an access token manually](#issue-an-access-token-manually) below) and use it as:

```json
{
  "mcpServers": {
    "vantage-peers": {
      "type": "http",
      "url": "https://vantage-peers-production.up.railway.app/mcp",
      "headers": {
        "Authorization": "Bearer YOUR_ACCESS_TOKEN"
      }
    }
  }
}
```

Access tokens are short-lived. Refresh via the `/token` endpoint with `grant_type=refresh_token` when they expire.

## Codex (OpenAI CLI)

Codex supports MCP via its `~/.codex/config.toml` (or project-level equivalent):

```toml
[[mcp_servers]]
name = "vantage-peers"
url = "https://vantage-peers-production.up.railway.app/mcp"
type = "http"

[mcp_servers.oauth]
client_id = "YOUR_CLIENT_ID"
client_secret = "YOUR_CLIENT_SECRET"
```

If your Codex build does not yet support the `oauth` block, fall back to a pre-issued access token in headers (same pattern as Claude Code above).

1. Save the config.
2. Restart `codex` so it picks up the new server.
3. List tools: `codex mcp list` should include `vantage-peers`.
4. Test: ask Codex *"call recall with query=hello"*.

## Google Antigravity

Antigravity reads MCP servers from one global file, `~/.gemini/config/mcp_config.json`. That single file applies to every workspace on the machine. Google's [MCP page](https://antigravity.google/docs/mcp) states that the configuration file "is located globally at `~/.gemini/config/mcp_config.json` (or locally in your workspace under `.agents/mcp_config.json`)". Google does not document how the two files are merged or which wins, and VantagePeers has not verified that the IDE loads the workspace file, so put the entry in the global file.

For the skills and the guided installer, see [Plugin](./plugin). The entry itself looks like this, with placeholders to replace by your seat's values:

```json
{
  "mcpServers": {
    "vantage-peers": {
      "serverUrl": "https://<your-vantagepeers-cloud-endpoint>/mcp",
      "headers": {
        "Authorization": "Bearer <seat token>",
        "x-vantage-agent-credential": "<agent credential>",
        "Content-Type": "application/json"
      }
    }
  }
}
```

Remote servers must use the `serverUrl` field. The `url` and `httpUrl` fields are not supported by Antigravity.

### Several agents on one machine

Create one entry per agent, named `vantage-peers-<agent>`, each with its own seat token and agent credential. Each agent's instructions must name the entry it uses. If two agents share one entry name, one of them silently acts with the other's identity.

```json
{
  "mcpServers": {
    "vantage-peers-<agent-a>": { "serverUrl": "https://<your-vantagepeers-cloud-endpoint>/mcp", "headers": { "...": "keys of agent A" } },
    "vantage-peers-<agent-b>": { "serverUrl": "https://<your-vantagepeers-cloud-endpoint>/mcp", "headers": { "...": "keys of agent B" } }
  }
}
```

### Check that it works

Restart Antigravity, then ask the agent: *"Check your messages, then send a message saying hello."* The MCP panel must show the entry enabled, with its tools listed.

<Callout type="warning">
Never paste keys into a chat, a commit, or a shared screen. Keep them in files only you can read.
</Callout>

### Other settings files: `settings.json`

A `~/.gemini/settings.json` (user) and a project `.gemini/settings.json` exist, but they belong to the Gemini CLI, not to Antigravity.

- Google's [Gemini CLI configuration reference](https://geminicli.com/docs/reference/configuration/) says the user file at `~/.gemini/settings.json` "Applies to all Gemini CLI sessions for the current user" and that the project file at `.gemini/settings.json` "Applies only when running Gemini CLI from that specific project" and "Project settings override user settings and system defaults". Gemini CLI reads `mcpServers` from these files ([Gemini CLI MCP page](https://geminicli.com/docs/tools/mcp-server/)).
- On the same MCP page, for a server provided by an extension, local `settings.json` values take precedence over the extension's defaults. That is the "local over extensions" rule: it concerns Gemini CLI extensions, not Antigravity.
- Google's [Antigravity CLI migration page](https://antigravity.google/docs/cli/gcli-migration) says: "Legacy Gemini config: Servers were declared inline within `~/.gemini/settings.json`" and that Antigravity CLI servers "are defined inside a standalone `mcp_config.json` profile".

Not verified by VantagePeers: whether the Antigravity IDE reads an `mcpServers` block from `~/.gemini/settings.json` or from a project `.gemini/settings.json`. No Google Antigravity page found says it does, and the migration page says the opposite for the CLI. For that reason this guide does not use `settings.json`, and a project-level file is not offered as a way to give each workspace its own entry. Keep one entry per agent in the global file, as above.

### Workspace plugin folder

Google's [plugins documentation](https://antigravity.google/docs/plugins) says a plugin folder placed in `.agents/plugins/` at the workspace root activates only for that project, and one placed in `~/.gemini/config/plugins/` activates for all workspaces. The VantagePeers installer does not use plugin folders: it installs skills into `.agents/skills/` and writes the MCP entry in the global file.

## Issue an access token manually

If your client cannot run OAuth automatically, you can run the PKCE flow yourself and paste the resulting access token in a `Bearer` header. Bash:

```bash
BASE="https://vantage-peers-production.up.railway.app"
CLIENT_ID="YOUR_CLIENT_ID"
CLIENT_SECRET="YOUR_CLIENT_SECRET"
REDIRECT="http://localhost:3000/callback"

# 1. PKCE verifier + challenge (S256)
VERIFIER=$(openssl rand -base64 64 | tr -d "=+/" | head -c 64)
CHALLENGE=$(printf "%s" "$VERIFIER" | openssl dgst -sha256 -binary | openssl base64 | tr -d "=" | tr "+/" "-_")

# 2. Print the authorize URL — open in a browser, accept consent, copy the `code` from the callback URL
echo "$BASE/oauth/authorize?response_type=code&client_id=$CLIENT_ID&redirect_uri=$REDIRECT&code_challenge=$CHALLENGE&code_challenge_method=S256&scope=mcp:full"

# 3. After consent, exchange the code for an access_token
read -p "Paste the code from the callback URL: " CODE
curl -s -X POST "$BASE/oauth/token" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=authorization_code" \
  -d "code=$CODE" \
  -d "client_id=$CLIENT_ID" \
  -d "client_secret=$CLIENT_SECRET" \
  -d "redirect_uri=$REDIRECT" \
  -d "code_verifier=$VERIFIER" | jq .
```

The response contains `access_token` (short-lived) and `refresh_token`. Send `Authorization: Bearer <access_token>` on every tool call.
